# Amendment 002 — `apikey` `+ext` columns reduce to `referenceId`; `revokedAt` deferred

**Status:** Accepted
**Date:** 2026-05-07
**Affects:** `DATA_MODEL.md §3 (apikey table)`; `sprints/sprint-0/brief-S0-02.md` AC #3 (apikey row); `sprints/sprint-0/brief-S0-03.md` AC #2 (apikey +ext columns).
**Author:** Sprint 0 manager; surfaced by S0-02 cursor IC, validated by S0-03 pi/deepseek-v4-pro IC, confirmed by S0-02 + S0-03 pi/kimi-k2.6 gate reviews.

---

## What changed

`DATA_MODEL.md §3` lists the following `+ext` columns on `apikey`:

```
apikey.organizationId  text    references organization(id) on delete cascade
apikey.revokedAt       timestamp
```

The actual schema at the end of S0-03 has neither column on `apikey`. Instead:

- `apikey.referenceId` (auto-generated by `@better-auth/api-key@1.5.5` when `references: "organization"` is configured) **is** the organization FK. Its semantic role is identical to what `DATA_MODEL.md §3` called `organizationId` — only the column name differs.
- `apikey.revokedAt` is **omitted** from the apikey schema at S0-03 close. The apiKey plugin's `ApiKeyOptions.schema` is typed `InferOptionSchema<ReturnType<typeof apiKeySchema>>`, which only allows renaming existing fields, not adding new ones (verified by reading `node_modules/.bun/node_modules/@better-auth/api-key/dist/types-CCe5L05Y.d.mts:205`). The plugin auto-generates an `expiresAt` column (Date, nullable) plus an `enabled` boolean (default `true`) — together those cover the practical revocation use case (set `enabled=false` and/or `expiresAt=now()`).

## What did NOT change

- The eight better-auth tables and all other `+ext` columns in `DATA_MODEL.md §3` ship as the doc spec'd them.
- The four-role access ladder (owner/admin/member/viewer) on the `organization` plugin.
- The personal-organization auto-create hook in `databaseHooks.user.create.after`.
- The `session.activeOrganizationId` seeding (now in `databaseHooks.session.create.after` per a related S0-03 amendment in the same commit; see `sprints/sprint-0/gate-S0-03.md §3.1`).

## Why

1. **`@better-auth/api-key@1.5.5` does not accept `additionalFields` on its schema.** The plugin's TypeScript surface (`ApiKeyOptions.schema`) is `InferOptionSchema<ReturnType<typeof apiKeySchema>>`, which strictly maps the plugin's built-in fields. Adding `organizationId` or `revokedAt` via `additionalFields` is not type-supported and would have to bypass the type system (which violates the "no shortcuts" rule in `.claude/CLAUDE.md §11`).
2. **`referenceId` is semantically equivalent to `organizationId`** when `references: "organization"` is configured — the plugin docs (<https://www.better-auth.com/docs/plugins/api-key>) state that `referenceId` is "the ID of the entity that owns this key (userId or organizationId based on the config's `references` setting)." Renaming for `+ext` parity would be cosmetic.
3. **Revocation is achievable through built-in fields.** `enabled: false` (existing column) and `expiresAt: <past timestamp>` (existing column) together cover the same product capability that `revokedAt` was meant to provide. A dedicated `revokedAt` column is recoverable post-MVP via a hand-authored supplement migration if a use case demands it (e.g., audit-log requires the exact revocation timestamp distinct from `expiresAt`).
4. **Sprint 0 is foundations.** The `apikey` table is not exercised by any application code in S0–S2 (programmatic API access is in BL-10 / public SDK backlog). Deferring the divergence resolution carries no risk.

## Resolution path forward

If at any point a feature requires the exact `DATA_MODEL.md §3` shape:

1. **For `organizationId`:** add a Drizzle relation alias mapping `referenceId` → `organizationId` at the query layer in `packages/core/repositories/`, OR ship a hand-authored supplement migration that adds an `organization_id` text column populated from `reference_id` (and a trigger to keep them in sync). Preferred: the alias path — zero schema change.
2. **For `revokedAt`:** ship a hand-authored supplement migration `packages/db/src/migrations/00xx_apikey_revoked_at.sql` that adds `revoked_at timestamp` to the `apikey` table. The application layer writes to it on revocation; queries that need to distinguish "revoked" from "expired" or "disabled" filter on `revoked_at IS NOT NULL`.

Both paths are non-disruptive and can land any time the use case appears.
