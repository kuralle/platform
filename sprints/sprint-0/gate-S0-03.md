## 3. The S0-02 amendments — audit

### 3.1 `session.create.before` → `session.create.after`

**Change:** `packages/auth/src/create-kuralle-auth.ts:156` moves the `activeOrganizationId` seeding from `session.create.before` to `session.create.after`.

**Audit against better-auth 1.5.5 source:**
- `node_modules/@better-auth/core/dist/types/init-options.d.mts:1105` declares `session.create.after?: (session: Session & Record<string, unknown>, context: GenericEndpointContext | null) => Promise<void>` — the API surface is valid.
- `node_modules/better-auth/dist/db/with-hooks.mjs` shows `.after` hooks are executed via `queueAfterTransactionHook`, i.e. **post-transaction**. This confirms pi's rationale: `.before` runs inside the transaction that creates the user/org, so `listOrganizations()` can't see the uncommitted org; `.after` sees the committed state.

**The `is_personal || isPersonal` snake_case fallback:**
- Still present at line 167 of `create-kuralle-auth.ts`. **Load-bearing and correct.** The `orgAdapter.listOrganizations()` call returns raw DB rows (drizzle-pg snake_case column names). The artifact `S0-03-rows.txt` shows the DB row has `is_personal: true`. The fallback is necessary because better-auth's `additionalFields` camelCase mapping only applies to its own internal serialization, not to the raw adapter rows returned by `listOrganizations()`.

**Verdict:** Amendment is correct, justified, and type-safe.

### 3.2 apiKey plugin config simplification

**Change:** Removed `schema.apikey.additionalFields` and the `as ApiKeyConfigurationOptions` cast. New shape: `{ references: "organization" as const }`.

**Audit against `@better-auth/api-key@1.5.5` types:**
- `ApiKeyConfigurationOptions` (from `types-CCe5L05Y.d.mts`) has `references?: "user" | "organization" | undefined`. The `as const` satisfies the literal type.
- The `ApiKeyConfigurationOptions` type has **no `schema` property** — `additionalFields` is not accepted. Pi's removal is technically required.
- The plugin auto-generates `referenceId` as the FK column. The migration SQL shows `reference_id text NOT NULL` with an index — this matches.

**Verdict:** Amendment is correct and unavoidable. The `ApiKeyConfigurationOptions` import is also removed (confirmed by grep).

## 4. The Gate-Partial framing — audit

**Pi's claim:** "Gate-Partial. Schema, migration, and hooks validated against local Postgres 15.12. neon-http + Workers path blocked."

**Honesty audit:**
1. **Did the sign-up E2E fail?** No. It passed against local Postgres + `pg`.
2. **Was it tested against Workers + Neon-HTTP?** No. `@neondatabase/serverless` uses an HTTP fetch protocol that cannot speak to `localhost:5432`. `alchemy dev` requires CF credentials. These are **infra blockers**, not code bugs.
3. **Does PLAN.md §0 cover this?** Yes. The pre-flight notes explicitly state: "Neon target deferred… The codegen gate is still satisfied because the better-auth-on-Workers + Postgres + Neon-HTTP-driver combination is exercised against a real Postgres 15.12."
4. **Is the gap documented?** Yes. `GATE-FAIL.md` (should be `GATE-PARTIAL.md`) lists four paths forward and recommends provisioning Neon.

**Smuggling audit:**
- Pi did **not** silently band-aid a failing gate. The commit body openly states the unchecked box (demo artifact) and the gate status.
- Pi did **not** re-interpret "sign-up E2E" into something easier — the smoke test exercises the same better-auth config, hooks, and DB schema that Workers would use. The only difference is the transport layer (`pg` wire vs. `neon-http` fetch).

**Verdict:** The framing is **honest and consistent with PLAN.md §0**. The file name `GATE-FAIL.md` is alarmist given the actual verdict in the body is `Gate-Partial`.
